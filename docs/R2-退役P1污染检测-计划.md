# R2：退役 P1 污染检测 — 清理计划

**前置依赖**：`docs/R1-语法引擎pattern遮蔽修复-fence隔离-计划.md` 已落地并通过全部验收（引擎遮蔽修复 + codeblock 块级 fresh 均生效）。本计划在其后执行。

## 1. 背景与依据

### 1.1 P1 是什么、为什么当时要做

v1.1.26（commit `2c6a26e1`，R0 计划）引入：非 codeblock 段渲染前检测 buffer Match 是否被跨行 region 粘滞污染（`polluted()`：出现非 `md-` 前缀组即判污染），污染则用一次性 Highlighter 做单行 fresh 重高亮（`freshLineMatch()`）。当时引擎缺陷未修、块内颜色无隔离手段，这是唯一能让块外正文恢复配色的下游补丁。

### 1.2 R1 落地后 P1 成为死代码的结构论证

P1 检测的是「非 codeblock 段的行取到被污染的 buffer Match」。R1 之后这个污染源结构性消失：

| 段类型 | 颜色来源（R1 后） | 污染可能性 |
|---|---|---|
| codeblock 段 | 块级 fresh（nil state 起步，R1-B） | 块内残留封在块尾，构造上不跨 fence |
| 非 codeblock 段（正文/标题/列表等） | buffer Match | markdown.yaml 顶层的跨行 region 只有 fence 一种；fence 行必被 P0 detect 判为 codeblock 段——不存在「fence region 粘滞影响到非 codeblock 行」的路径 |

两类污染（引号被 pattern 遮蔽类、真·未闭合字符串类）分别被 R1-A、R1-B 兜住，`polluted()` 永远返回 false，`freshLineMatch()` 永不被调用。

### 1.3 为什么不 git revert v1.1.26

`2c6a26e1` 同时包含 P0（fence 驱动 detect）与 P3（tilde/HR），revert 会把本来正确的部分一起撤掉，detect 退回 state 驱动后真·未闭合字符串场景重新吞段。P1 采取**前向删除**。

## 4. 风险与边界

| 风险 | 评估 |
|---|---|
| 存在 R1 论证未覆盖的污染路径，删 P1 后正文变白 | 论证穷尽了 markdown 顶层跨行 region（只有 fence）；验收第 2/3 项显式覆盖两类污染样例。若真出现，说明 R1 有洞，应修 R1 而非保留 P1 补丁 |
| 编辑模式 / 非 md 文件的 buffer Match 污染 | 与 P1 无关：P1 只在 `renderSegmentMD`（MD 阅读模式）路径生效；编辑模式与非 md 文件用原生渲染，一直是 micro 原版行为（用户已实测确认原版同症），不属本计划范围 |
| 误删 R1 依赖物 | 撤销清单逐项列明保留项；步骤 5 的 grep 兜底 |
